The fill-instant fast path: how it works, and does it hold?

An explainer for ADR-153/154/155 and docs/contributing/fill-instant-proofs.md (branch design/808-fill-instant-fast-path @ 6c7eb0b8, PR #811). Built 2026-11-07 from an independent model written to try to break the proof. That model is separate from the proof author's scripts. The design is not implemented; "before" numbers come from the real library on main, "after" numbers come from the model.

Verdict

The core argument is sound. On a single limit with fixed parameters, the two conditional writes never over-admit by more than a clock-skew term, whatever the interleaving. In 484 simulated runs of the design the worst case reached 0.61 of that term, and every deliberately broken variant was caught. The proof has two gaps that over-admit as written: positive adjustments, and requests larger than the capacity in force. It also has one statement in ADR-153 that needs amending for schedules with skew, and less integer headroom than the author estimated. Each has a small fix, and with the fixes the model passes everywhere. Details are in Findings.

1. The bug, measured on the real library

Issue #808. A limit of 300 per 4 hours (one token every 48 s). The entity uses 1 token, idles a day, then sends 700 requests at 1000/s. A strict token bucket admits about 300. The library on main admits 599:

Cumulative admissions after a day idle

Real library on moto with a frozen clock (one request per ms), against the fill-instant model and the strict bound C + r·t.

Why: the stored balance tk, request by request

The fast path subtracts from tk but never moves rf (last refill), which stays a day old. When tk hits 0, the slow path credits the whole idle day, refills to 299, and the bucket is drained a second time.

The root cause is that a full bucket should forget how long it has been full, and the fast path does not. It records "300 tokens, last refilled a day ago", which the next materialising pass reads as "a day of refill is owed".

2. The idea: store when the bucket will be full again

A dripping limit's whole state is one number, its fill instant z: the moment the balance is (or was) back at capacity.

balance(t) = C − r · max(0, z − t) any z ≤ t reads as full

Admitting c tokens at time t (write d = c/r, the time the tokens take to drip back):

admit iff z ≤ t + (C − c)/r then z ← max(z, t) + d

The max is the "forget the idle time" step. DynamoDB has no max, but each side of it is easy:

WriteCondition (checked by DynamoDB)UpdateExact when
N (not full)t ≤ z ≤ t + (C−c)/rz ← z + dthe bucket is not full
F (full)z < tz ← t + dthe bucket is full

On any admissible item exactly one of the two conditions holds, and it records exactly max(z,t)+d (Lemma 1). If the client guesses the wrong side, the write fails, nothing changes, and the failure returns the item, so the second write is chosen from the truth. The client's guess never decides admission; the server's condition does.

The kink, and why one write can't do it (Theorem 2)

x-axis: where the fill instant was relative to now. y-axis: where it must be recorded after admitting c = 3 on a bucket with C = 10, r = 1/s. A DynamoDB update is affine: a straight line. The exact answer bends at z = t, and no single line follows both arms. N is exact on the right arm, F on the left. Today's fast path uses N's line everywhere; on the left it records too early (the shaded area), and that forgotten idle time is #808.

The aqua line is the best a single safe write can do (Corollary 1). To never over-admit, it must record every admission on a full bucket as emptying it (balance 0 instead of C − c), which throws away the bucket. Hence two writes.

3. Why it stays safe with many consumers (Theorem 1)

Each consumer reads its own clock once per request (the stamp t), and its writes land at real instants T. The proof compares the item with an imaginary reference bucket Y fed the same applied writes at the real instant each one landed. Let e = z − y be how far the item's fill instant is from the reference's, and o = t − T each write's offset (clock skew plus time in flight), with s = max |o|.

  • Returns and adjustments move both by the same amount, so e is unchanged.
  • An admission on the same side in both views either leaves e alone or resets it to that write's offset o.
  • An admission where the item and Y disagree about full lands e between its old value and o.

So |e| can never exceed s, whatever the interleaving. Since every admission passed its condition on the item, Y never goes below −2rs, which gives the bound: tokens admitted in any window ≤ C + r·w + 2·r·s. No lock is needed, because every write is an exact step on whatever item it finds.

e / s over a run: 24 consumers, 0.5 s clock skew, up to 0.2 s in flight, returns and debt

Each point is one applied write. The proof says every point stays within ±1. e moves only when an admission finds the bucket full in one view; during a busy burst it holds (the flat runs), and each burst after an idle gap restarts it from that write's offset.

4. Does it hold? A fuzz campaign

Each scenario runs 12–40 seeds of an event-driven model: Poisson or bursty arrivals, per-consumer clock offsets, random flight times, leases that return tokens or add debt, retries reusing the stamp, and a cap answering "contended". For every run the checker takes the worst window over every pair of events (not a sample) and reports excess / 2rs, where excess is admitted minus C + R(w). Up to 1 means the bound holds. The BROKEN rows run the same traffic through deliberately wrong writes, to show the checker catches violations.

5. How many writes? (Theorems 3 and 4)

Other consumers' admissions only push z later (Lemma 2). An image showing "not full" is therefore always still right; only "full" can go stale. With the stamp reused on every retry, each limit can flip from full to not full at most once, so a request decides within L + 1 writes when it guesses "full" everywhere, or L + 2 otherwise. I built the adversary that forces every flip: both bounds are reached exactly.

Writes needed against the worst-case adversary, by number of limits L

Returns break the cap (Theorem 3c). If another consumer may return tokens between your writes, it can keep you undecided for ever (six writes shown; it goes on as long as B wants). Below, B admits 2 tokens before A's full write and returns them before A's not-full write, so A is always on the wrong side. The design's answer is a write cap and a "contended" 429: an under-admission, never an over-admission.

6. What it costs: guessing the side

A wrong guess costs one failed write (1 WCU, one round trip). With Poisson traffic at utilisation u the bucket is not full with probability u, so a blind guess is wrong at min(u, 1−u). I re-implemented the proof's §6 table (300 per 4 h, 1-token requests, 200k requests per cell) and got the same numbers to within about 2 points:

First-write misprediction rate

Left: 4 consumers, right: 32. The reference line is min(u, 1−u). A plain image rule collapses at high load with many consumers, because a stale image almost always shows "full".
Table view, with the proof's numbers

One open item the proof also flags: the "extrapolate" predictor uses the true u, and how a client would estimate it is unspecified. With bursty on/off traffic (4 h on, 12 h off, mean u = 0.5) all three predictors were wrong 2–12% of the time, so burstiness made things easier here, not harder.

7. The other writers (ADR-155)

Shard splits

A raise from S to 2S shards reads every shard. Then, in one transaction pinned on what it read, it trims each shard to the new share and gives the sibling the excess. Across 200 simulated splits (1→32, with writes racing them), the total balance before and after differed by at most tokens: float rounding, so it is conserved exactly. The window bound held at of the clock term. The control, today's "new shard starts full" (ADR-133), exceeded it by tokens.

Schedule boundaries

Balance across a boundary from 0.1x to 1x (per_minute(1000), drained at 05:59:00)

Today the slow path credits the whole minute at the rate in force at the end (1000 tokens at 06:00:01). Re-expressing at the boundary drips the first minute at 0.1x and caps it at 100 (116.67 at 06:00:01).

8. Findings

1 · over-admitsA positive adjustment is not exact as written

The proof's write table, §7, and ADR-155 ("adding to the fill instant for a return, adjustment or top-up") treat lease.adjust(+c) as an unconditional z ← z + d. That is exact only if the bucket is not full. Debiting c from a full bucket must record max(z, t) + d, the same kink as an admission. When z + d < t, the debt is forgiven entirely. Returns and top-ups are fine, because min(C, b + c) is exactly what z − d gives.

This is the LLM reconciliation case: estimate 100 tokens, the call takes 2 minutes, the bucket refills to full meanwhile, then adjust(+900) lands. In the model, adding the adjustment that way pushed |e| to 72× s and the window excess to 17× the clock term. Theorem 1 misses it because its reference bucket uses the same y ← y + d rule, which is not the strict bucket's.

Fix: a positive adjustment is a forced debit. Send the same N/F pair as an admission, without the upper bound (exactly the soft-limit form). It can take two writes, and retries when returns interleave. Treated that way: 0.28× of the clock term, with |e| ≤ s.

2 · over-admitsThe full write admits a request larger than the capacity

§1 assumes 0 < c < C, but F's condition is only z < t. If c > C, F admits on a full bucket and leaves the balance at C − c < 0. This is reachable: a schedule window with scale < 1, or a sharded share C/S below the request (#475). In the model a 17-token request passed against a 0.1× window with C = 10 (36× the clock term, worst of 40 seeds). Fix: for a hard limit, the client must refuse c > C before sending F. It can, because the write is pinned on the parameters it computed C from. ADR-154's decision text should say so.

3 · statementADR-153's ceiling "in force at the window's start" is wrong under skew

At a boundary that lowers capacity, a consumer with a slow clock can still spend from the old, larger ceiling for up to s after the boundary, before the re-expression trims it. Measured literally against the ceiling at the window's start, the schedule runs failed by 3–54×. With "the largest ceiling in force from s before the window's start to its start", every run passed (≤ 0.08×). The design is fine; the sentence in ADR-153 (and Theorem 5) needs that wording. Theorem 1 is unaffected: it fixes the parameters.

4 · marginInteger headroom is about 1.3 orders of magnitude, not about 8

ADR-154 stores z × refill amount. With the #570 ceilings (MAX_TOKENS 1e15, MAX_SCALE 1e6) the effective refill amount reaches 1e24 millitokens. Times an epoch-ms stamp (1.8e12 today, 4.1e12 in 2100) that is 4.1e36, against DynamoDB's 1e38. The proof author's 1.8e30 leaves out schedule scale. It still fits, but those ceilings were chosen to sit 14 orders inside 1e38, and this design spends 12 of them. A future ceiling raise, or an unbounded adjust() amount pushing z far into the future, would overflow (boto3 raises decimal.Rounded).

Smaller notes

  • Lemma 2's wording: "only a return moves z earlier". Resets, top-ups and re-expression also do. The theorems that use it (3b, 4) assume admissions only, so nothing breaks, but the lemma should say so.
  • The lower bound's scope (M3): M3 excludes more than presence-based encodings. It also excludes any encoding where z is a max of stored attributes (conditions can test max(a,b) ≤ X as a ≤ X AND b ≤ X). I tried to build one with a bounded number of attributes and failed: dropping a term is unsafe unless it is known to be dominated, which needs the same side information. This matters only for the claim that two writes are optimal. The safety proof does not depend on M2 or M3.
  • BatchExecuteStatement could send N and F together and let one fail, but DynamoDB rejects two statements on the same item in a batch (DuplicateItem), so it cannot beat the lower bound.
  • The s in the bound grows with retries. Every retry reuses the original stamp, so s covers clock skew plus the whole retry sequence (up to the cap × the round trip). That is small (tens of ms), but it is not just skew.
  • A reset forgives debt (z ← t). That matches ADR-149's reset-to-full, but is worth stating explicitly for dripping limits, as ADR-151 D12 does for soft quotas.
  • Not modelled: ADR-145 quota moves inside ADR-155's doubling transaction, top-ups and resets on sharded entities, and the integer arithmetic itself (the model uses floats).
